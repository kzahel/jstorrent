# Tactical 345: Never Reset Shipped Catalogs; Migrate Forward

Status: Complete, 2026-10-14. Maintainer-directed safety slice; commit
authorized. Prerequisite for Tactical
[344](344-seeding-stop-limits.md), which adds the first real migration.
Topics: `client-persistence`, `beta-release-readiness`,
`capability-readiness`.

## Problem

Every public release since `android-v0.1.0` and `desktop-v0.1.4`, including
all JSTorrent production releases (`desktop-v0.3.0`/`0.3.1`,
`android-v1.0.29`–`1.0.31`), ships session catalog schema 26. Schema 19
shipped only in RSTorrent incubation desktop `0.1.0`–`0.1.2` and Crostini
`0.1.0`; schema 22 only in incubation desktop `0.1.3`. Table definitions at
every schema-26 tag match HEAD; no schema change has happened since the public
release, so no user profile has been reset.

The open path still treats every version below `SCHEMA_VERSION` as a
disposable incubation catalog: `profile_reset::prepare_catalog` deletes
`session.db` and creates a fresh one. Bumping `SCHEMA_VERSION` to 27 in any
tactical would therefore silently delete every user's torrents, settings,
verified-piece state and statistics on their next launch. The documents still
describe the catalog as disposable until a future "first supported"
declaration (`client-persistence`, `release-baseline.md`,
`beta-release-readiness` REL-005), although the product has shipped.

## Decision

Maintainer direction, 2026-10-14:

- Losing user data on upgrade is unacceptable. The application never resets,
  replaces or discards a session catalog on its own. The only path that
  discards it is the user's explicit Clear app data.
- Schema 26 is the supported baseline. Every later schema change ships a
  hand-written forward migration step and is proven against fixtures produced
  by released code.
- Older pre-baseline catalogs (19, 22) and future catalogs fail closed and are
  left byte-for-byte unchanged. Downgrade is not supported.
- Old schema definitions are not kept; they are history in git.

## Scope

### Catalog open path

- Remove the automatic reset: the reset marker, exclusive reset lock and
  catalog deletion in `profile_reset.rs`, and creation of new
  `profile_reset_report` rows. The table remains part of the frozen baseline;
  an unpublished report from an earlier reset is still read and acknowledged.
- `prepare_catalog` classifies the stored version:
  - absent database or zero-length file: create;
  - current version: open;
  - baseline ≤ version < current: migrate;
  - 1 ≤ version < baseline: fail with a retired-schema error, unchanged;
  - version 0 with content, or above current: fail, unchanged.
- An empty (zero-byte) `session.db` still becomes a fresh catalog, because it
  holds no data.

### Migration runner

- `store_migration.rs` owns an ordered list of steps; step *i* migrates
  `baseline + i` to `baseline + i + 1`. A compile-time assertion requires
  `baseline + steps == SCHEMA_VERSION`, so bumping the version without a step
  does not build.
- Fresh catalogs are created as the frozen baseline (`create_schema_26`,
  never edited again) followed by every step, so fresh and migrated catalogs
  are identical by construction. With no steps yet, fresh creation is
  unchanged.
- Migration runs every pending step and each `user_version` update in one
  `BEGIN IMMEDIATE` transaction that rechecks the starting version. A crash
  or error rolls back to the untouched old version, and the next open retries.
- Before the first step, the runner copies the catalog through SQLite's online
  backup API to `session.db.pre-migration` (written to a temporary name,
  synced, then renamed). Only the most recent pre-migration copy is kept; Clear
  app data removes it with the other private profile files. A failed backup
  aborts the migration and leaves the catalog unchanged.

### Fixtures and guards

- A populated schema-26 catalog generated by the release tag
  `android-v1.0.31` code is checked in under
  `crates/rstorrent-session/tests/fixtures/catalog/v26.sqlite`, with its
  generator and provenance. The generator is an ignored integration test
  that uses only the public store API, so it runs unmodified in a worktree at
  the tag.
- Tests:
  - every released fixture opens with current code, and every row of every
    fixture table survives unchanged except columns a migration step
    documents;
  - a migrated fixture's `sqlite_master` equals a fresh catalog's exactly,
    which also catches edits to the frozen baseline;
  - the runner, with synthetic steps, commits all steps atomically, rolls back
    a failing step leaving the original version and bytes, and writes the
    backup first;
  - retired, unversioned and future catalogs are refused without any file
    change; the existing malformed, symlink and busy cases remain.

### Documentation

- `AGENTS.md`: a short durable-data rule pointing at `client-persistence`.
- `client-persistence`: the supported-baseline contract, how to write a
  migration step and fixture, and the release obligation to add a fixture for
  each newly released schema version.
- `release-baseline.md` and `beta-release-readiness` REL-005: record schema 26
  as the declared persistence baseline and no automatic reset.
- `capability-readiness`: record the change.

## Other Durable Formats

Audited 2026-10-14. Most stores fail closed, default one bad field, or clear
only from an explicit user reset:

- `product.db` migrates in place (schema 1 → 2, `product_state.rs` 724-740)
  and refuses newer versions unchanged. `metrics.db` refuses an unknown
  version and runs with unpersisted history without deleting the file
  (`speed.rs` 1090-1112, 1516-1517).
- Android SharedPreferences stores default unknown values per field; the SAF
  root registry and data-reset journal are versioned and fail closed; legacy
  JSTorrent import only fills absent keys and never deletes its source.
- Web `rstorrent.presentation.*` keys fall back to defaults on a version
  mismatch and are rewritten only when the user changes a setting. The remote
  client IndexedDB refuses newer versions.
- Remote authority files, gateway web-auth, companion pairings and headless
  TOML refuse unknown or corrupt state without rewriting it.

Follow-ups, outside this slice:

1. Desktop `desktop-shell.json` (`desktop_lifecycle.rs` 82-93, 154-167)
   rewrites itself with defaults for any version other than 3 or 4, an
   unknown field or a parse error, losing background, notification and power
   choices. On macOS and Windows the reset `network_defaults_version` then
   makes the next start hold the listener and port mapping Disabled in the
   session catalog (`lib.rs` 2443-2452, `store.rs::hold_unconfirmed_network_features`).
   Downgrade is unsupported, but a corrupt or partially written file reaches
   the same path. It should fail closed or default per field.
2. Extension `productMetricsV1` (`clients/extension/src/product-metrics.js`
   119-135, 184-192) replaces the whole stored value on any shape difference,
   re-enabling statistics after a user opted out and issuing a new
   installation ID. A privacy regression risk; it should keep the opt-out.
3. Web table layouts (`VirtualTable.tsx` 194-200, 1327-1392) are rewritten on
   mount after a version mismatch and drop unknown column IDs. Cosmetic.

## Non-Goals

- Downgrade support, export/restore, or automatic recovery from the backup.
- Migrating schema 19 or 22 catalogs.
- Any schema change; Tactical 344 adds 26 → 27.
- A startup recovery UI for refused catalogs beyond the existing startup
  failure presentation.

## Invariants

- No code path other than the user's Clear app data removes or replaces a
  nonempty `session.db`.
- A refused catalog, its WAL and auxiliary files are not modified.
- A migration either commits every step or leaves the original version and
  contents; the pre-migration copy exists before the first change.

## Validation

- `cargo test -p rstorrent-session`, workspace `fmt`, `clippy` and `test`.
- Fixture provenance: the generator run at `android-v1.0.31` and its output
  digest.

## Evidence

- Every release tag's `SCHEMA_VERSION`: 19 for desktop `0.1.0`–`0.1.2` and
  Crostini `0.1.0`, 22 for desktop `0.1.3`, 26 for every later tag through
  `desktop-v0.3.1` and `android-v1.0.31`. The table, index and constraint
  definitions at `android-v0.1.0` and `desktop-v0.3.0` match HEAD apart from
  two test-only triggers.
- The generator ran unmodified in a worktree at `android-v1.0.31`
  (`70150ec99ff5613bb468fd816fed46c687ff7557`) and produced
  `tests/fixtures/catalog/v26.sqlite`, SHA-256
  `499e32a3ba498ee3d0743e8b13d6f9c09a08f497572303dedfbe262c8c008bfa`. Its
  `sqlite_master` equals the same generator's output at HEAD.
- `cargo test -p rstorrent-session`: 404 library tests pass (2 ignored), plus
  the integration targets; `cargo clippy -p rstorrent-session --all-targets
  -- -D warnings` is clean. New coverage: version classification; retired
  (1, 18, 19, 22, 25) and future catalogs refused with bytes and directory
  listing unchanged; empty, absent, leftover-auxiliary, malformed,
  unversioned, symlink and busy shapes; pre-migration copy contents and
  replacement; Clear app data removes the copy; the released fixture opens
  with every row and the fresh schema; the baseline definitions equal the
  released catalog; the runner commits steps atomically and rolls back a
  failing step, a foreign-key violation and a stale starting version.
- Negative controls: setting `SCHEMA_VERSION` to 27 without a step fails to
  compile; widening one baseline `CHECK` fails both fixture tests.

## Stopping Condition

Complete when the automatic reset is gone, the migration runner, backup,
classification and guards are implemented and tested against the released
fixture, the documents above record the contract, and the client-side audit is
recorded.
