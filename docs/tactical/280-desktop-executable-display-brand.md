# Tactical 280: Desktop Executable Display Brand

Status: Complete locally, 2026-10-08. Maintainer-directed finish-line branding correction.

Topics: `client-surfaces`, `product-surfaces-and-migration`,
`beta-release-readiness`.

## Scope and stopping condition

The final signed Windows x64 NSIS rehearsal shows that newly created native
firewall rules use `rstorrent-desktop.exe` as their display name. Product and
permission-dialog screenshots are branded, but this OS-facing label remains.
Tactical258 deliberately retained internal binary names; the actual system
label evidence now justifies this bounded desktop output filename correction.

Name the desktop output executable `jstorrent-client`, including ordinary Cargo
and packaged builds. Keep the Rust package/library names, native-host binary,
identifiers, updater routes/keys, profiles, migration and networking unchanged.
Use a distinct name from retired `jstorrent-desktop`, `jstorrent` and `JSTorrent`
so the existing old-writer process fence keeps its accepted behavior. Do not
add firewall permissions/rules or rewrite inherited OS rules for branding.

Update installed-package validators, both Windows packaging workflows, Linux
notification icon selection and exact-binary rehearsal selection. Historical
source8c runs must remain reproducible with an explicitly selected historical
filename. Do not rewrite historical receipts or call local unsigned evidence a
signed Windows display-name pass.

Stop when local output/package checks and proportional Rust regressions pass,
owning topics are reconciled, and the exact-source signed rebuild/requalification
requirement is recorded. Actual final Windows firewall/system labels and native
migration/updater evidence require new signed bytes under Tactical259.

## Validation

- Cargo target metadata and desktop release/package validators require the new
  main executable, retaining platform identity and quoted associations.
- Existing legacy process-name regression rejects the distinct successor name
  while continuing to recognize all released old-writer names/truncations.
- Native notice collection recognizes both the new first-party executable and
  historical source8c output; native library attribution/security gates remain.
- Historical and current rehearsal filename selection is explicit and bounded.
- Focused package/distribution tests, desktop/native-host Rust tests and clippy,
  formatting and actual local unsigned bundle inspection where available.
- Fresh signed five-target build, installed Windows OS label, migration and
  updater qualification remain separate required execution under259.

## Result and remaining signed evidence

The Cargo main binary and default-run are `jstorrent-client`; package/library
names remain `rstorrent-desktop`/`rstorrent_desktop`. Existing Windows install
probes and Mac/Linux/Windows activation validators now require the branded
filename. Linux notifications use the corresponding generated icon name.
Both rehearsal drivers accept an explicit bounded historical filename selector;
current default is the new name. Registry restoration includes its application
key. Native notices require one desktop executable plus the unchanged host,
accept either current or historical output and refuse both/missing variants.

All41 focused Node package/release/candidate cases,23 native distribution cases,
85 desktop/native-host Rust cases, focused clippy, formatting, Cargo metadata
and workflow lint pass. The actual unsigned/debug production-identity macOS
bundle builds and validates: CFBundleExecutable is `jstorrent-client`, the
executable is present, old desktop output is absent, and the independent
six-entry distribution inventory/notices passes. This is file/package evidence;
no installed Windows label, signature or native migration/updater pass is
inferred from it. [Tauri configuration reference](https://v2.tauri.app/reference/config/#mainbinaryname)
recommends setting the Cargo output target when possible rather than renaming
only inside the bundler; metadata and the actual bundle verify that selection.
